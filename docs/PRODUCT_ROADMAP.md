# AniWatch — продуктовая дорожная карта

Этот документ фиксирует согласованные направления развития AniWatch. Использовать его как постоянный ориентир при планировании и выполнении следующих обновлений. Не внедрять все пункты автоматически: перед каждой задачей проверять актуальность, зависимости, безопасность и влияние на уже работающий функционал.

## Принципы разработки

1. Сначала стабильность и исправление регрессий, затем новые функции.
2. Перед крупными изменениями создавать резервную ветку или иной проверяемый способ отката.
3. Делать небольшие изолированные изменения; не менять соседние части сайта без необходимости.
4. Не считать задачу завершённой только потому, что код написан: проверять CI, миграции, деплой и по возможности пользовательский сценарий.
5. Не заявлять о визуальном или сквозном тестировании, если оно фактически не проводилось.
6. Сохранять текущую визуальную идентичность AniWatch. Не возвращать брендинг сторонних каталогов/провайдеров в интерфейс.
7. Не ухудшать текущую систему источников аниме и загрузку постеров ради экспериментов. Отдельно проверять совпадения постеров у разных тайтлов.
8. Для социальных функций учитывать приватность, RLS, права доступа, защиту от спама и корректную работу при выходе из аккаунта.
9. Все изменения интерфейса и пользовательских сценариев проверять и адаптировать для ПК и мобильных устройств.
10. Приоритет — полезные, законченные пользовательские сценарии, а не количество функций.

## Приоритет 0 — стабилизация уже сделанного

- Проверить вкладку «Вместе»: актуальность данных, обновление после действий, Realtime-подписки, состояния для гостя и авторизованного пользователя.
- Проверить добавление в друзья: поиск по нику, отправка запроса, принятие/отклонение, удаление из друзей.
- Проверить приглашения на совместный просмотр: отправка другу, принятие/отклонение, срок действия, переход в нужное аниме и эпизод.
- Проверить поведение после обновления страницы, повторного входа и на разных устройствах.
- Честно обозначать ограничения синхронизации внешних плееров. Не обещать синхронные паузу/перемотку, пока они реально не реализованы и не проверены.
- Проверить влияние ограниченных прав таблицы profiles на регистрацию, профиль, никнейм и аватар.

### Раздел «Мои списки» — критическая стабилизация

- **Проблема отмечена пользователем:** раздел «Мои списки» работает очень плохо; требуется отдельная диагностика и исправление, прежде чем считать его надёжным.
- Пересмотреть загрузку пользовательских списков через Supabase/БД: для авторизованного пользователя получать актуальные данные из БД как основной источник истины, а не полагаться на устаревшее локальное состояние.
- Устранить медленную, неполную или нестабильную загрузку; проверить запросы, индексы, RLS-политики, обработку ошибок и состояния загрузки/пустого списка.
- После добавления, удаления или изменения тайтла корректно обновлять данные в БД и интерфейсе; исключить потерю изменений и рассинхронизацию между устройствами.
- Сохранить разумный локальный fallback для быстрого открытия и временной недоступности сети, но синхронизировать его с БД без перезаписи более свежих серверных данных.
- Проверить все типы списков (например, смотрю, запланировано, просмотрено, отложено и избранное), повторный вход, обновление страницы и работу на ПК/мобильных устройствах.
- Не считать исправленным только после изменения кода: проверить реальные сценарии авторизованного пользователя и права RLS.
- После стабилизации — добавить понятные уведомления о новых запросах в друзья и приглашениях.

### Совместный просмотр через Kodik — проблема подтверждена пользователем

- **Подтверждено пользователем:** при запуске просмотра через Kodik функция «Вместе» не работает.
- Пользователь предоставил документацию Kodik Player API: события `kodik_player_*` принимаются через `postMessage`, команды управления отправляются с ключом `kodik_player_api`.
- В `js/core/streaming-player.js` используется Kodik Player API: приём событий времени, длительности, play/pause/seek/speed/current_episode/video_ended и отправка команд play/pause/seek/speed через `postMessage`. Сообщения принимаются только от текущего iframe.
- **Улучшена коррекция рассинхронизации:** при большой разнице времени отправляется seek; при небольшой — кратковременная коррекция скорости с возвратом к скорости ведущего после выравнивания. Добавлена обработка ответа `kodik_player_time` и ограничено избыточное вещание обновлений времени.
- В состояние комнаты передаётся длительность видео. Переключение серии через селектор Kodik ведущего теперь транслируется участникам, которые переходят на соответствующую страницу просмотра.
- Повторный запрос состояния после готовности iframe сохранён, чтобы не терять начальное состояние комнаты.
- **Синхронизация озвучки добавлена в код:** ведущий передаёт ID перевода Kodik вместе с состоянием воспроизведения; участник находит соответствующий релиз в собственном списке доступных озвучек, переключает iframe и восстанавливает позицию/скорость/состояние. Если у участника такого ID нет в доступных релизах, переключение не может быть выполнено автоматически. Требуется ручной тест двумя аккаунтами и проверка совпадения ID переводов в выдаче Kodik.
- **Проблема запуска аниме ещё не подтверждена как исправленная.** Пользователь уточнил, что ломается именно запуск просмотра через код комнаты, а не только синхронизация таймлайна. Первоначальный запуск внутри iframe может требовать клика пользователя из-за autoplay-ограничений браузера; команда `play` не может гарантированно обойти это ограничение.
- Нужен end-to-end тест двумя реальными аккаунтами: ведущий создаёт комнату и запускает Kodik; гость входит по коду, открывает тот же тайтл/эпизод, вручную запускает видео при необходимости; далее проверяются play/pause/seek/speed/смена серии, обновление страницы и мобильный браузер.
### Аудит входа в комнату по коду — 10.11.2026

- Найдена ошибка: прежний обработчик пытался открыть первую запись из локального массива каталога вместо получения состояния комнаты; в актуальном потоке это не давало корректно определить аниме и эпизод.
- Исправлен сценарий: гость подключается к Realtime-каналу по коду и запрашивает состояние у ведущего; после ответа с текущими animeId/episode открывается правильная страница просмотра.
- Текст интерфейса уточнён: ведущий должен уже находиться на странице просмотра. Ограничение синхронизации таймлайна для внешних плееров остаётся в силе.
- Проверка двумя реальными аккаунтами не выполнена: ожидает второго аккаунта/согласованного тестового аккаунта. До неё считать исправление технически реализованным, но не подтверждённым end-to-end.

## Приоритет 1 — социальная система

- Основной пункт «Вместе» убран из главной навигации; вход в поиск друзей и совместный просмотр перенесён в профиль отдельной карточкой. Прямой URL `together.html` и функции приглашений сохранены.
- В профиле добавлена переключаемая настройка автоматического перехода к следующей серии. По умолчанию включена; выключение не мешает вручную выбирать следующую серию.

### Сохранение выбранной озвучки Kodik

- Исправляется потеря выбранной озвучки при переходе на следующую серию: ID перевода сохраняется локально отдельно для каждого аниме и автоматически выбирается при загрузке следующей серии.
- Если сохранённый перевод отсутствует в списке доступных для конкретной серии, плеер использует доступный вариант; выбор пользователя не считается гарантированно доступным на стороне Kodik.
- Сохранение локальное для этого браузера/устройства; синхронизация предпочтения между устройствами не заявляется.

### Уведомления

- Единый центр уведомлений.
- События: запрос в друзья, принятие запроса, приглашение на совместный просмотр, выход новых серий у тайтлов из списка пользователя и другие важные события.
- Счётчик непрочитанных и отметка прочитанного.
- Настройки типов уведомлений и возможность отключить ненужные оповещения.
- Не спамить повторными уведомлениями об одном событии.
- Для новых эпизодов показывать, к какому аниме они относятся, номер серии и дату выхода, если источник предоставляет достоверные данные.
- Не обещать точное время выхода, если расписание или источник ненадёжны.

### Профили и присутствие

- **Первый этап редактора профиля:** редактирование ника удалено по запросу; ник только отображается. Описание остаётся редактируемым.
- **Публичные профили и приватность:** добавлены настройки «все пользователи / друзья / закрытый профиль», отдельные переключатели показа статистики и избранного. Ник и аватар остаются доступны для поиска друзей; содержимое профиля защищено. Публичные профили доступны и гостям; режим «друзья» требует принятой дружбы, закрытый профиль доступен только владельцу. Доступ к описанию, баннеру, агрегированной статистике и избранному выдаётся через RPC `get_public_profile`, который проверяет владельца, режим приватности и принятую дружбу. Прямой SELECT-доступ к `bio`, `banner_url` и настройкам приватности отозван; прямой доступ к `user_library` не расширяется. SECURITY DEFINER используется намеренно для чтения только агрегированных/разрешённых данных поверх owner-only RLS.
- **Проверено на БД:** rollback-only тест подтвердил, что закрытый профиль не раскрывается другому пользователю, владелец видит собственный профиль, а при скрытом избранном его количество также не выдаётся. Приватные поля не читаются напрямую через таблицу `profiles`.
- **Ожидает ручной проверки:** переход к публичному профилю из поиска друзей, копирование ссылки, сохранение настроек и проверка видимости с аккаунта друга/постороннего аккаунта.


**Первый этап редактора профиля — реализован в коде, ожидает CI и ручную проверку:**
- Добавлены редактирование ника и краткого описания (до 280 символов).
- Добавлена обложка профиля с загрузкой в существующее хранилище `avatars`; аватар сохранён и продолжает работать.
- Для авторизованного пользователя ник, описание и обложка загружаются/сохраняются через Supabase; для гостя — локально.
- На странице профиля сохранена статистика и добавлен блок избранных тайтлов.
- Добавлены поля `bio` и `banner_url` в `profiles`; RLS-политики не ослаблялись, права UPDATE выданы только на нужные поля.
- Требуется проверить сохранение/повторную загрузку профиля, загрузку баннера и аватара, а также мобильную вёрстку. Публичные страницы пользователей, настройки видимости, любимые персонажи, публичные коллекции и лента активности остаются отдельными следующими этапами.

- Развить профили пользователей: баннер, аватар, описание, любимые аниме и персонажи.
- Показывать публичную коллекцию и выбранные пользователем списки.
- Добавить персональную статистику просмотра: просмотренные тайтлы и серии, время просмотра и другие проверяемые показатели.
- Статус онлайн/не в сети и время последней активности — с настройками приватности.
- Лента активности друзей: что смотрят, что добавили в список, что завершили. Пользователь должен иметь возможность скрыть активность.
- Предусмотреть приватность профиля и отдельных элементов: публично, только друзьям или скрыто.

### Личные сообщения

- Личные сообщения между друзьями.
- Базовые текстовые сообщения и история диалога.
- Защита от сообщений посторонних, блокировка/ограничение пользователей и антиспам.
- Не начинать с тяжёлого real-time чата, пока не стабилизированы дружба и уведомления.

## Приоритет 2 — совместный просмотр

- Постоянные комнаты, к которым можно вернуться по приглашению или ссылке.
- Общая очередь аниме/эпизодов.
- Голосование за следующий тайтл или эпизод.
- Состояния участников: смотрит, отошёл, закончил.
- Синхронизация воспроизведения: play/pause/seek и текущая позиция — только там, где плеер и источник технически позволяют надёжно управлять воспроизведением.
- Реакции во время просмотра.
- История совместных просмотров.
- Понятное отображение ведущего комнаты и прав участников.
- Обработка отключения, повторного подключения и рассинхронизации.

## Приоритет 3 — просмотр и навигация

### Экспериментальная интеграция Anixart API

- Исследовать неофициальный API Anixart как дополнительный источник данных, не заменяя Shikimori и текущие источники до проверки качества и стабильности.
- Первый прототип проверить на одном тайтле (например, «Ван-Пис»): сопоставление тайтла, русское название/описание, фактически доступные серии, озвучки и ссылки на просмотр.
- Отдельно проверить требования авторизации, актуальные базовые URL, CORS, лимиты запросов и риск блокировок; не запрашивать и не хранить пароль пользователя Anixart.
- Если интеграция подтвердит пользу, реализовать серверный адаптер/прокси с ограничением частоты запросов, кэшированием метаданных и fallback на текущие источники. Не размещать токены в клиентском JavaScript.
- Не показывать название Anixart или других внешних провайдеров в интерфейсе AniWatch.
- Считать интеграцию исследовательской задачей: API неофициальный, может меняться и не гарантирует постоянную доступность потоков.


### Умная лента «Продолжить просмотр»

- Отдельный заметный блок с тайтлами, просмотр которых пользователь уже начал.
- Для каждого тайтла показывать последнюю известную серию и, если доступно, позицию внутри серии.
- Кнопка «Продолжить» должна открывать страницу просмотра и вести к нужному эпизоду; при технической возможности — восстанавливать позицию воспроизведения.
- Сохранять прогресс между устройствами для авторизованного пользователя.
- Не перезаписывать более свежий прогресс устаревшими данными с другого устройства.
- Предусмотреть ручное исправление серии и удаление тайтла из ленты.
- Не считать серию просмотренной автоматически, пока механизм отметки не работает надёжно и не проверен.

### Удобный выбор серии

- Поиск и быстрый переход по номеру эпизода.
- Компактный список доступных серий с понятным текущим состоянием.
- Кнопки перехода к предыдущей и следующей серии.
- Отображение доступности серий и вариантов просмотра на основании фактических данных источника.
- Не показывать несуществующие эпизоды и не путать номер серии с внутренним ID.
- Удобное управление на мобильных экранах, без чрезмерно высокой панели плеера.

### Умный поиск

- Поиск по русскому, английскому и японскому названиям.
- Поддержка поиска по жанрам, студии, году, сезону и статусу выхода.
- Нормализация регистра, пробелов и распространённых вариантов написания.
- Понятные подсказки и быстрый переход к странице тайтла.
- Устойчивое поведение при недоступности одного из источников: ошибка отдельного источника не должна ломать весь поиск.
- Не перегружать внешние API запросами; использовать debounce, разумное кэширование и ограничения параллельных запросов.
- Поиск должен быть удобен как на ПК, так и на мобильных устройствах.

## Приоритет 4 — персонализация и рекомендации

- Перепроверить и восстановить полноценную логику рекомендаций: учитывать историю и оценки пользователя, а не только локально закешированные карточки.
- Сделать устойчивое получение кандидатов: отказ одного источника или жанрового справочника не должен обнулять всю выдачу.
- Учитывать просмотренное, избранное, скрытое и явно неинтересное.
- Добавить возможность исключать тайтлы/жанры из рекомендаций.
- Показывать объяснение рекомендации: общие жанры, похожие оценки, связь с просмотренными тайтлами.
- Раздел «Похожие вкусы» между друзьями.
- Подборки малоизвестных тайтлов («скрытые жемчужины»).
- Не допускать повторов и уже просмотренных тайтлов без явной причины.
- Добавлять интеграционные тесты всего пути: профиль вкусов → кандидаты → ранжирование → отображение.

## Приоритет 5 — каталог, сообщество и достижения

- Комментарии к отдельным эпизодам.
- Маскировка спойлеров с раскрытием по нажатию.
- Пользовательские коллекции и списки.
- Пользовательские оценки и короткие отзывы.
- Календарь выхода эпизодов — только если источник данных стабилен и не создаёт чрезмерную нагрузку.
- Статистика просмотра и персональные итоги за год.
- Достижения за осмысленные действия: знакомство с разными жанрами, завершение тайтлов, активность в коллекциях и другие проверяемые события.

### Приоритет 2 — синхронизация прогресса (в работе)

- В клиенте уже есть локальное хранение IndexedDB с fallback на localStorage и синхронизация с `user_library`.
- Восстановление прогресса выбирает более свежую позицию по `history.at`, а отметки просмотренных эпизодов объединяет.
- **Исправлено на уровне БД:** применена миграция `20261110004856_user_library_progress_conflict_guard`. Перед UPDATE/UPSERT триггер сравнивает время прогресса и не даёт старому устройству затереть более свежую позицию; отметки эпизодов объединяются.
- **Проверка БД:** выполнен rollback-only тест на временной записи — более старый прогресс не заменил новый, более новый был принят, списки просмотренных серий объединились. Тестовая запись удалена; проверка подтвердила, что тестовых строк не осталось.
- Функция триггера не имеет EXECUTE для `anon` и `authenticated`; Security Advisor не добавил новых предупреждений безопасности.
- **Ограничение:** объединение отметок эпизодов сейчас аддитивное. Снятие отметки просмотренной серии на одном устройстве ещё не синхронизируется как отдельное событие удаления.
- **Дополнительно реализовано:** HTML5-плеер передаёт фактическую длительность медиа вместе с текущей позицией; история сохраняет `duration`, а карточка «Продолжить просмотр» рассчитывает полосу прогресса по реальной длительности, а не по условным 23:40. В карточке явно показан номер серии, переход ведёт сразу к ней.
- **Совместимость:** если источник не предоставляет длительность (например, внешний iframe), карточка всё равно открывает сохранённую серию, но не рисует выдуманный процент прогресса.
- **Исправлено дополнительно:** при открытии выбранной серии теперь сразу сохраняется запись `animeId → episode` с нулевой позицией, если источник не отдаёт события воспроизведения (например, внешний iframe). Это позволяет показывать аниме в «Продолжить просмотр» без выдуманного времени/процента; HTML5-плеер продолжает обновлять фактическую позицию.
- **Подтверждено пользователем:** после последнего исправления выбранное аниме начало появляться в истории/ленте «Продолжить просмотр». Кросс-девайс сценарий по-прежнему требует отдельной ручной проверки.
- **Проверка БД после обновления:** повторный rollback-only тест подтвердил, что старый snapshot не затирает позицию и duration; новый snapshot принимается, отметки серий объединяются. Тестовая запись удалена.
- **Остаётся проверить:** два реальных устройства/браузера, вход в один аккаунт, продолжение серии на устройстве A, восстановление на устройстве B, затем обратное обновление и сценарий офлайн → онлайн. Не считать кросс-девайс сценарий полностью проверенным до этого теста.

### Отдельная идея — умный поиск по описанию аниме (отложено)

- **Статус:** идея зафиксирована, не реализована; не включать в текущие задачи без отдельного решения пользователя.
- **Концепция:** пользователь описывает сюжет своими словами (например, «парень переродился в другом мире и начал качать мышцы»), а поиск находит аниме по смыслу, а не только по названию и буквальному совпадению слов.
- **Предполагается платный внешний ИИ API:** LLM (например, GPT или аналог) для разбора запроса и выделения сюжетных признаков; embeddings для смыслового поиска по описаниям; Supabase PostgreSQL + pgvector для хранения векторов и поиска; обычный текстовый поиск используется совместно для гибридного ранжирования.
- **Принцип экономии:** embeddings описаний каталога рассчитывать заранее и обновлять при изменении данных, а не генерировать заново для каждого поиска. API-ключ хранить только на серверной стороне (например, в Supabase Edge Function), не в клиентском коде.
- **Зависимости перед реализацией:** проверить доступность и стоимость выбранного embedding/LLM API, лимиты и тариф Supabase, полноту русскоязычных описаний, объём каталога и возможные ограничения по запросам.
- **Ожидаемый интерфейс:** отдельный режим «Умный поиск» рядом с обычным поиском; обычный поиск должен продолжать работать независимо от платного API.
- **Ограничение:** не обещать точные проценты совпадения без калибровки на тестовом наборе. Нужны тесты на запросах с несколькими признаками (реинкарнация, другой мир, магическая академия, тренировки/мышцы, скрытая сила и т. п.).
- **Важно:** Anixart API не исследовать и не подключать в рамках этой идеи без отдельного разрешения пользователя.

### Дополнение: отдельная модель прогресса серий — 10.11.2026

**Статус: PR #35 объединён в main и опубликован; CI и Pages deployment успешны. Требуется сквозной тест на двух устройствах.**

- Создана public.user_episode_progress с ключом (user_id, anime_id, episode), флагом is_watched и серверным updated_at.
