# AniWatch — продуктовый аудит и план развития

Дата: 8 ноября 2026  
Основа: исходники ветки `main`, структура SPA, модули страниц, API-клиенты, CSS, Service Worker и доступные публичные страницы конкурентов.

## Краткий вывод

AniWatch сейчас лучше позиционировать как **аниме-каталог и персональный трекер**, а не как готовый стриминговый сервис. В проекте есть интерфейс плеера, но нет подключённого видеопотока; совместная комната и чат работают только локально в текущем браузере. Пока нет собственного backend, нельзя обещать межустройственную синхронизацию или полноценные аккаунты.

Основные продуктовые приоритеты:
1. достоверные данные и корректные подборки;
2. поиск и каталог;
3. личная библиотека и перенос данных;
4. расписание и сезонная навигация;
5. цельный адаптивный интерфейс;
6. только после этого — серверные функции и просмотр.

## Технические находки

### Критично
- Страница просмотра прямо говорит, что плеер демонстрационный и видеоисточник не подключён.
- Комнаты и чат не синхронизируются между браузерами: код комнаты хранится в локальном состоянии.
- До текущей работы главная собирала тренды, онгоинги и «недавно добавленное» из одной 30-тайтловой подборки, а затем сортировала её по разным полям. Это создавало ложные подписи разделов.
- При полном отсутствии сети и локального кэша стартовый массив демонстрационных тайтлов мог показываться вместо реального каталога.

### Высокий приоритет
- `js/app.js` всё ещё содержит крупный объём контроллеров и API-логики после первого модульного рефакторинга.
- `css/style.css` содержит повторяющиеся селекторы и несколько слоёв переопределений. Полная нормализация нужна отдельным этапом с визуальными регрессионными проверками.
- Основная навигация содержит слишком много пунктов для нижней мобильной панели.
- Профиль честно хранит данные локально, но пока не предоставляет экспорт/импорт.

### Ограничения платформы
- GitHub Pages — статический хостинг. Без backend нельзя реализовать настоящие аккаунты, межустройственную синхронизацию комнат, серверный чат и безопасное хранение пользовательских данных.
- Источники метаданных (AniList/Shikimori и дополнительные сервисы эпизодов) могут иметь разные значения и задержки обновления. Нужны единые правила приоритета и маркировка происхождения данных.
- Реальный видеоплеер нельзя считать готовым только потому, что интерфейс плеера существует. Источник видео должен быть легальным и устойчивым.

## Изменения в этой рабочей ветке

- Главная получает отдельные выборки AniList для трендов, популярного, онгоингов и недавно вышедших тайтлов через один GraphQL-запрос.
- Главная не выдаёт размер загруженной подборки за размер всей базы. Поле `pageInfo.total` не используется для статистики: официальная документация AniList предупреждает, что `total` может быть неточным.
- Подписи блоков приведены к смыслу соответствующих сортировок.
- При недоступности API и отсутствии кэша не показываются выдуманные демо-карточки: появляется понятное состояние с повторной загрузкой.
- Основная навигация сокращена до пяти основных разделов; «Вместе» убран из главной навигации до появления реальной серверной синхронизации, но сам раздел не удалён.
- Service Worker cache version поднята до `aw-v40`.

- Не добавлять десятки эффектов до стабилизации данных.
- Не делать вид, что демонстрационный плеер воспроизводит видео.
- Не внедрять платную инфраструктуру без необходимости и отдельного решения.

## Проверка

Сайт GitHub Pages не удалось открыть инструментом визуального просмотра в ходе аудита. Поэтому визуальные выводы основаны на CSS и шаблонах, а не на заявлении о полноценном браузерном тестировании. Перед слиянием изменений обязательны синтаксическая проверка всех модулей и проверка опубликованного сайта в реальном браузере.
